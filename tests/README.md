# Tests

The test modules import `bpy`, so they run inside Blender, not with a system Python. The repository
directory *is* the add-on package.

## Command

From the repository root:

```sh
blender --background --factory-startup --python tests/run_tests.py
```

`run_tests.py` puts the repository's parent directory on `sys.path`, enables the package with
`addon_utils.enable(<repository directory name>, default_set=True)` (that is what creates the
`AddonPreferences` entry the add-on reads), discovers `tests/test_*.py`, runs them with
`unittest` at verbosity 2, and exits `0` on success / `1` on failure.

Blender's background mode has no *current* area, and `WM_OT_y_open_image_as_layer` reads
`bpy.context.area`; the runner therefore wraps the suite in a `temp_override` pointing at the
background window's first screen area. Without it, ten tests error out.

### Undo (real window)

Blender's undo stack is not usable from `--background` (`bpy.ops.ed.undo.poll()` is False and
driving it corrupts the shared scene), so the T-7b undo tests skip there. Run the same modules in a
real window under Xvfb:

```sh
./tests/run_ui.sh
```

`run_ui.sh` starts a private X server and strips the Wayland session variables before launching
Blender; a bare `xvfb-run blender` still opens a window on a Wayland desktop (the leaking
`WAYLAND_DISPLAY` did exactly that before `038d0d2`). It also applies a hard
timeout (`UI_TIMEOUT`, default 300 s), and the UI scripts carry a watchdog (`UI_WATCHDOG`, default
240 s), so a failure can never leave a window or a process behind. Set `BLENDER_BIN` to run a
specific build (`BLENDER_BIN=/path/to/blender ./tests/run_ui.sh`; default: `blender` from `PATH`).

`run_tests_ui.py` enables the add-on, waits for one event-loop tick (the undo stack exists only
once the event loop has run), and discovers/runs `tests/test_*.py` from a timer callback with a
`VIEW_3D` context override. In that mode `TestCustomUndo` runs; in the headless command it reports
four skips.

## Assumptions

- **`--factory-startup` is required.** Without it Blender loads the user's enabled add-ons first,
  which can collide with this package, and a previously saved scene/preferences change the result.
- **Startup scene.** `tests/test_quicksetup.py` does not create a scene: it expects the factory
  startup file's active object `Cube` with a material named `Material` (its node tree holds the
  Ucupaint group node).
- **The add-on must be registered** before the tests: they call `bpy.ops.wm.*` operators such as
  `y_quick_ypaint_node_setup`, `y_new_layer`, `y_remove_yp_node`.
- The tests mutate the current scene, so every run needs a fresh Blender process and
  `--factory-startup`.
- Test `test_quicksetup.py` defines `TestCase` subclasses that inherit from each other
  (`TestNewMask(TestOpenImageAsLayer)` etc.), so the suite reports 33 tests for 13 methods; that
  is expected.

## Verified

- Blender 4.2.9 LTS, headless: `Ran 159 tests ... OK (skipped=4)` (the four undo tests), exit 0;
  acceptance script `docs/specs/001-custom-node-layer/acceptance_5_2_3.py` 15/15 PASS; UI runner
  through `./tests/run_ui.sh`: `Ran 159 tests ... OK`, exit 0.
- Blender 4.5.9 LTS, the same three runs with the same results, exit 0.
- Blender 5.2.3 LTS (extension build, reference), headless: `Ran 159 tests ... OK (skipped=4)`,
  exit 0; acceptance script 15/15 PASS (see `acceptance-5.2.3.md`).
- Blender 5.2.3 LTS, UI runner through `./tests/run_ui.sh`: `Ran 159 tests ... OK`, exit 0,
  including the undo tests.
- The 4.2/4.5 builds come from `/tmp/opencode/blender-builds` (outside the repository). No leftover
  Blender processes after any run.
- One 4.2/4.5 difference is handled in the tests: `NodeTreeInterface.new_socket()` rejects
  `NodeSocketMenu` before 5.0, so `TestCustomSocketFilter` probes the capability instead of
  assuming it (`6ce4e43`).
- Not verified: GPU/EEVEE rendering (all runs are headless CPU), and `acceptance_5_2_3_undo.py` on
  4.2/4.5 — the undo unit tests do run in the UI suite there.

## Notes

- Running the add-on writes a `<package name>_updater/` folder next to the repository root on
  registration (generated by `addon_updater_ops`); delete it before committing.
